# 先对齐需求，再自动执行

新目标默认先读取并使用 [包内 grill-me](modules/grill-me/guide.md)。这就是统一包中的技能调用，不要求用户另装 grill-me。先读已有讨论和代码；能查清的事实直接查，不把技术调查交给用户。

## 对齐方式

先按目标选深度：局部修复只处理受影响行为；完整功能追踪一条从输入到结果的用户路径及错误状态；项目改造追踪所有承诺路径、现状与目标的差距、跨模块接口、兼容与交付。不能因为默认在当前会话执行，就把项目改造当成局部修复。

围绕当前任务依次解决会改变实现的决定：用户要达成的结果、使用场景、范围与不做的事项、可观察的验收标准，以及 AI 可自行决定什么、遇到什么必须回来问。自动运行还要明确预算、停止条件和交付终点。按依赖关系选择问题，每次只问一个，并给推荐答案及主要取舍。问题数量由未解决的决定分支决定，不以一两个问题作为完成访谈的标准；已有完整答案时也不凑数。

## 项目级访谈的决策树

先读代码和已有规格，把下面适用的主题列成决定记录；每项说明答案/依据或下一步。按照“目标 → 用户路径 → 范围 → 行为边界 → 接口/数据 → 验收/交付”追问，先解决会影响后续问题的决定。

| 主题 | 需要查清的内容 |
| --- | --- |
| 目标与现状 | 谁遇到什么问题；现有实现哪些可复用、哪些缺失；这次怎样算解决 |
| 用户路径 | 角色、入口、主操作、成功结果；有哪些承诺路径，优先级与完整交付终点 |
| 范围 | 每条诉求本轮实现、已有满足、延期或不涉及；延期需要实际用户依据 |
| 界面 | 页面与交互；加载、空白、错误、权限、保存/撤销和适用视口 |
| 数据与服务 | 数据所有权、字段、校验、接口契约、旧数据兼容与迁移恢复 |
| 访问与外部依赖 | 身份、角色边界；第三方失败、重试、重复操作的结果 |
| 质量与运行 | 适用的性能、隐私、可访问性、运行环境与观测；具体可验收边界 |
| 验收与自主权 | 行为例子、自动检查与人工判断；预算、停止条件、交付终点 |

区分五类记录：**已有答案**（引用真实消息/规格）、**代码调查**（引用事实）、**待问用户**（缺偏好/业务决定，带推荐方案）、**授权自定**（可逆实现细节，记录依据）、**不适用**（原因）。没有查到的事实继续调查，不能用“用户未指定”把业务边界当成实现细节。用户可回答的未知决定优先追问，不自行以最小实现替代完整目标。

收敛条件是适用主题已有依据、关键问题解决、每条诉求有明确处置和验收。单纯达到问题数、用户说“可以”但不对应具体范围、或有一张简单流程图，都不是收敛依据。结构化检查与记录字段见 [plan-depth.md](plan-depth.md)。

## 确认与实施

收敛后给用户一份简短需求摘要，包含目标、范围、验收、约束和自动执行边界。用户对此表示确认，或已有同等具体的确认时，记录原话和来源。确认的是明确的需求，不再额外询问一次“是否允许开工”。只要求讨论或计划的任务仍止于其指定终点。

小修改可用一句摘要完成对齐。确认后自动完成模块拆解和执行计划，进入规划—执行—验证—反思循环；常规实施和重试不逐步请示。

## 对齐记录

交互任务优先把记录写入已有计划开头，无约定时用 `.workflows/<任务>/requirements.md`。新计划引用同一份记录，避免维护多份规格。自动执行把下列对象放入串行或协作计划的 `requirements_alignment`，并随计划固定摘要；[JSON 模板](../assets/requirements-alignment.example.json) 默认 draft，不能原样开跑。

- `method: grill-me`；`mode` 为 interview、reuse 或 user_requested_skip。
- `status: confirmed` 只能来自实际用户确认；草稿用 draft。
- `goal`、`scope`、`acceptance`、`autonomy`：分别记录目标、边界、验收标准、可自行决定事项和运行/交付限制。
- `user_confirmation.reference` 与 `quote`：可追溯的用户消息或用户维护规格位置，以及对应原话。
- `open_questions`：尚需决定的问题。自动启动时必须为空，不能为通过检查删掉未解决问题。
- reuse 时还写 `reused_from`，指向同目标的已确认记录。只有用户明确要求省略访谈时，才使用 user_requested_skip，并在确认原话中保留该指令；“你自己做”不能被泛化为所有后续任务都免对齐。

Python 检查记录完整、确认状态和未决问题；它不能鉴定一句话是否真的出自用户，也不能判断摘要与任务语义是否一致。启动方必须核对真实对话/规格与当前任务，不能由执行模型自造确认。记录不是新的推送、部署或费用授权。

## 续跑、分支和需求变化

同一目标的续跑和控制器分配的子任务继承记录，核对范围与版本后直接实施，不重新访谈用户。旧记录缺失时先从真实对话恢复；不能把一次测试或过去的完成报告自动当成需求确认。

改变用户体验目标、数据语义、范围或验收标准时，暂停受影响任务，回到 grill-me 只问新增决定；无影响且已授权的任务可继续。实现细节、可逆重构和既定预算内修复由 AI 自行处理。夜间无法取得必要答案时保存具体问题与推荐方案，保持受影响任务 blocked；不能让 AI 总控代替用户回答偏好问题。固定快照需要变更时保留现场，再准备新快照。

2.3 起对齐记录必填。2.4 的串行计划仍为 v4，协作计划为 coordinated v2，增加需求覆盖与人工答复。历史运行使用其冻结版本复现；跨版本迁移需根据真实确认准备新快照，不能修改旧计划摘要绕过检查。v2 同一快照内的补充答案和人工签收按 [人工答复与续跑](human-resume.md) 处理，不需重新建计划。
