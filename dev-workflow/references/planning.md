# 模块拆解与执行计划

所有进入本工作流的新开发目标按此顺序推进：读取现状 → [grill-me 对齐需求并记录用户确认](requirements-alignment.md) → 模块拆解 → 编写执行计划书 → 检查计划就绪 → 实现与验收。初步阅读、定位和相称的基线检查属于准备阶段。需求已对齐且有实施授权时，计划就绪后连续执行；用户只要求计划时，到计划书为止。

## 先拆解模块

按能说明职责和验证结果的功能边界拆解，沿用已有架构。只列本次涉及的模块；明确的小修改可以只有一个模块。模块清单本身不代表要新增微服务、目录或子代理。

为每个模块给出稳定 ID、名称、职责与边界、输入、输出、依赖模块和验收结果。全栈工作明确界面、服务端和数据之间的接口；可以采用业务功能模块并在内部列出前后端工作，不机械地把所有任务都拆成一套固定层次。相互循环依赖的部分先明确共用契约，或合并为同一协同模块。

先完成模块清单，再将工作细化成任务。节点标题遵循所选语言，用具体动作，如“Validate login” / “校验登录”、“Generate report” / “生成报告”；完整实现要求放 `goal`，不要把工作者提示词当标题。初始任务和动态新增任务遵循同一约定；同屏标题应能区分。不要用“分析、开发、测试”三个阶段名称代替真正的功能模块。

## 从模块拆到可验收节点

模块是职责分组，图上的节点是具有输入、产出和结束依据的工作单元。项目改造不能把整个前端或整个后端交给一个笼统节点。出现不同产出、不同依赖、可独立验证的行为或失败时需要不同恢复动作，就考虑分开；同一产出的机械小动作保留在节点内部。

例如完整预约功能可涉及“核对现状、对齐规则、约定接口、设计状态、迁移数据、校验冲突、创建预约、取消预约、预约表单、结果列表、异常反馈、联调路径、核验权限、核验兼容、审阅改动、交付报告”。这些是示例，只有实际适用才创建；不能自动生成并标记前置访谈完成。真实项目可以更多，局部错误修复可以只有定位/修复和验证。

每个节点写清：所属模块、具体行为、前置产物、允许范围、输出、相关需求/验收条件、适用技能、检查方式。界面状态、数据迁移、业务错误、集成与回归不能藏在一句“完善功能”里。检查本身工作量或依赖不同就单列验证节点；项目级交付至少明确最终验收和审阅工作。

交付新增或修改的测试时，固定验收还要实际运行这些项目测试，并确认有测试被收集；不能只证明业务行为通过另一份外部检查，再把测试文件的存在当成可运行。命令和隔离环境由准备阶段明确，外部启动器可以固定待交付的测试路径，不让工作者改验收来凑通过。干净克隆/首次启动的修复，要验证真实共享数据库的初始化顺序及受影响的旧入口，不能用分离数据库或替身应用证明生产配置兼容。

普通会话中的细节点由当前 AI 连续推进，不需要每个节点都开分支或启动模型。多分支模式按可独立合并的工作包派工，工作包内保留具体步骤和活动回报；不能把流程图节点数等同于工作者数量。分支依赖、冲突和共享契约沿用协调协议。

项目级交互任务按 [plan-depth.md](plan-depth.md) 保存同一份结构化计划，用脚本检查需求遗漏、未决主题、依赖和验收覆盖，再生成计划书和可见节点。既有夜间 v2/v4 计划沿用原协议，在任务目标、只读计划资料、需求与验收中保留同样的细度，不添加协议不支持的字段或重写运行快照。脚本提示大任务时人工审查语义；拆分仅改善计划，不自行扩大用户范围。

## 再写执行计划书

使用 [执行计划书模板](../assets/execution-plan.template.md)，按实际规模删减空章节；小修改保留目标、单模块说明、执行步骤与验收方式即可。已有 PRD、模块文档或计划能够覆盖这些信息时，引用并补全原记录，不复制第二份相互冲突的计划。

计划书至少明确：

- **目标与范围**：用户要完成的行为、本次交付终点、已有约束和明确不涉及的事项。
- **模块设计**：模块清单及接口和依赖关系，选用的前后端技术栈与设计依据。
- **执行任务**：稳定任务 ID、所选语言的简短标题 `title`（中文 2–12 字、英文 2–40 字符，可选双语 `titles`）、所属模块 ID、前置任务、具体步骤、允许改动的文件或模块、指定技能、产出和验证方法。跨模块联调任务可以关联多个模块。
- **执行顺序**：先决条件、阶段顺序、每阶段开始和结束条件。先打通一条能运行的功能路径，再扩展其余功能；使用串行执行器时串行运行，使用协作执行器时明确里程碑、共享约定、分支消息及资源互斥。
- **验收与恢复**：相关基线、实际检查命令或操作、证据保存位置、失败处理、阻塞项及下一步。工期与费用不确定时记录估计依据，不虚构精确承诺。

grill-me 是新目标的前置入口；Taste、Impeccable 和 backend-development 等按 skill-routing.md 分工。计划书承接已经确定的答案和确认来源，不能让下游技能重新发起相同访谈。

## 保存与就绪检查

优先使用项目既有计划位置；没有约定时，在 `.workflows/<任务短名>/plan.md` 保存，按模块拆解在前、执行安排在后的顺序编写。项目不允许辅助文件时存入当前任务允许的输出目录，向用户给出位置。需要持久化进度时使用同目录的 state.md，链接计划书，避免复制规格。

开工前按 [验收覆盖与计划一致性](acceptance.md) 核对：需求均有验收条件，每条条件有自动检查或人工验收方式；每个模块有任务；消费方任务确实依赖提供必要产物的任务；前后端接口没有矛盾；会改变产品目标、技术栈或交付范围的关键决定已解决。结构检查不能替代需求语义和测试有效性的审查。

交互开发中发现事实变化，先更新受影响的模块或步骤，记录变更依据，再推进；不为无关细节重写整份计划。续接时核对已有计划与 Git 状态，恢复到未完成步骤，不重复执行已经验收的任务。先打通主路径后，继续补齐范围表中的其他承诺；交付前逐条对照原始需求、任务与证据。不得以“本轮只做基础版”悄悄删去已承诺路径，实际无法完成时明确剩余项与原因。

## 夜间计划衔接

采用多分支控制器时，使用 [协作 v2 计划](coordination.md) 的 requirements 清单，把已确认的每条需求关联到任务、独立检查或人工审阅，并将该对应表写进执行计划书。开工前对照原始确认复核是否漏掉整条诉求；脚本只能验证已列出的需求及引用关系。

准备阶段先完成模块方案，再写任务步骤与验收安排；将这些内容填写到 v4 night-run.json 准备数据，使用 `render-plan` 编写正式计划书。需求、模块、任务、依赖与验收表来自同一份数据，具体命令和约束保存在文档附录中。计划书就绪后填回 execution_plan 路径/摘要，再由控制器固定整份 JSON。这样保留先规划后编码的顺序，并避免人工维护两份执行规则。

将计划书及所引用的必要接口/需求资料复制到控制器管理的运行目录，作为本轮只读输入。`execution_plan` 固定计划书快照本身；引用资料由控制器一并版本化，不从可变网页或另一份聊天里临时补齐关键决定。若先把计划书存进仓库，应在创建执行工作区之前按项目约定纳入准备基线，避免计划文件让工作区变脏。

控制器在模型执行前固定 night-run.json 的摘要。`preflight` 和 `verify` 核对需求覆盖、模块与任务依赖绑定、计划书摘要，以及根据准备数据重新生成的整份文档。模块依赖通过任务的 module_dependencies 绑定到产物提供任务，执行顺序由任务 depends_on 推导。

夜间执行不能自改模块范围、执行计划书或其摘要来绕过检查。2.5 的新协调运行可按 [受控重规划](replanning.md) 在既定范围内版本化调整实施依赖/新增准备任务；原验收、授权和预算保持固定。超出此协议或旧串行快照需要变化时保留现场，再准备新快照。内容一致不能证明业务方案合理、原始需求无遗漏或确实先于编码产生，仍需准备阶段审查。
