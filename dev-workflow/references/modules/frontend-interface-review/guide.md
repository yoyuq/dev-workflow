# 前端界面综合审查

将“前端界面综合审查”视为执行完整流程的请求，不要求用户分别输入 critique、audit 等命令。依赖当前已安装的 Impeccable；本技能负责组织范围和合并报告，具体评审方法以实际安装版本为准。

## 范围与默认行为

- 默认审查当前项目的主要前端页面和关键用户流程，只审查，不修改业务代码、不自动修复、不重新设计。
- 用户指定页面、组件、路径或 URL 时，以指定范围为准。结合当前任务上下文和工作目录定位项目；仅在无法定位或存在实质歧义时询问目标。
- 先列出页面/路由、关键流程、共享组件及现有设计规范。按真实产品用途确定检查范围，不将营销页审美套用到后台或数据界面。
- 页面很多时优先覆盖每种独立页面类型、共享组件、关键流程及其状态，清楚报告抽样范围，不能把抽样说成逐页全量检查。
- 允许生成本次审查报告、截图和必要的临时预览文件。不要为了审查自动初始化 PRODUCT.md、重建 DESIGN.md、修改项目配置或安装持久化 hooks。
- 如果用户同时明确要求修复，先完成审查，再按其授权范围继续修复；否则以报告结束，不自动进入修复阶段。

## 加载 Impeccable

1. 从当前技能目录中定位 `impeccable/SKILL.md` 并读取，解析其真实技能根目录。常见位置为 `~/.agents/skills/impeccable`、`$CODEX_HOME/skills/impeccable` 或 `~/.codex/skills/impeccable`；不要将开发本技能时的用户名写死。
2. 读取该目录的 `reference/critique.md` 和 `reference/audit.md`。原生应用使用 Impeccable 对应的平台指引，不将 Web 检测器用于原生界面。
3. 按其 Setup 在待审查项目目录中运行一次 `context`。Windows 使用技能根目录下的 `scripts/impeccable.cmd`，其他环境使用 `scripts/impeccable`；不要假设项目内存在一份 skill。
4. 若启动器失败，按 Impeccable 的降级流程读取已有项目上下文并继续可执行的检查，明确缺失证据。若整个 Impeccable 技能缺失，说明依赖不可用，不声称完成了 Impeccable 审查。

## 综合执行

先完成 critique 的独立评估，再补齐 audit 的技术检查。遵循其独立子代理、检测器、浏览器证据及权限要求；已有适用授权时直接继续，未授权时按当前环境和 Impeccable 的要求处理。缺少工具或权限时如实标注降级。

保留 critique 对设计判断和检测证据的隔离，避免在独立设计评估结束前用检测器结论影响它。已有同一版本、同一目标的有效证据可以复用到 audit，不重复启动整套扫描。需要追加检查时只补缺失维度。

检查以下维度，并按实际产品需求判断适用性：

| 维度 | 检查内容 |
| --- | --- |
| 视觉与设计一致性 | 布局、字体、配色、间距、对齐、视觉层级、设计 token、组件一致性、产品特征与模板化问题 |
| 用户体验与信息架构 | 导航、可发现性、关键任务流程、认知负担、操作反馈、文案和信息组织 |
| 状态与边界 | 加载、空状态、错误、成功、禁用、表单校验、长文本、重复提交、适用的国际化与内容溢出 |
| 可访问性 | 语义结构、键盘操作、焦点、标签、对比度、辅助技术相关实现和减少动态效果偏好 |
| 响应式与交互 | 桌面、窄屏与必要的中间断点，布局溢出、触摸目标、导航变化及真实可验证的手势行为 |
| 技术质量 | 前端性能、资源加载、渲染与动画成本、已有主题切换、实现完整性和设计系统偏移 |

- 同时检查源码与实际渲染页面（可访问时），验证关键操作。只有 URL 时说明源码检查受限；只有代码且无法运行时说明视觉与交互未验证。
- 区分静态推断、实际运行测量、模拟视口、合成触摸和真机验证。不编造性能指标或可访问性合规结论。
- 保留原有品牌及产品约束。未要求暗色主题、国际化或某种审美时，不把未实现该能力自动列为缺陷。
- 逐项复核检测器命中，去除误报；需要进一步验证的猜测单列，不当作已确认问题。
- 不进行无限循环审查。集中收集证据、补足关键缺口并形成报告；本次仅为审查启动的服务按 Impeccable 要求清理。

## 合并报告

输出一份中文报告，合并 critique 与 audit 的重复发现，按共同根因归并跨页面问题。遵循当前任务要求的输出位置；聊天中必须给出主要结论，不能只给文件路径。

报告包含：

1. **范围与验证方式**：项目、页面、流程、视口、检查方式；独立评估的执行或降级状态；未覆盖和未验证的部分。
2. **总体评价**：设计与体验结论、技术检查结论、按严重程度统计的问题数，以及值得保留的优点。若沿用 Impeccable 评分，将设计与技术评分分开；不适用或未验证的维度明确标记，不强行合成总分。
3. **问题清单**：为确认的问题分配稳定编号 `UI-001` 等，按 P0 → P1 → P2 → P3 排序；相同级别优先列出影响关键流程、影响范围广的问题。
4. **优先修复项**：最多 5 个最值得先修的问题，解释优先理由，并给出后续修复顺序。
5. **检查限制**：无法访问、缺少账号/数据/运行环境以及需要进一步验证的内容。

每个问题包含：编号、严重程度、页面/组件/文件位置、可复现步骤或证据、用户影响、具体修改建议、修复后的验收方法、适合的 Impeccable 后续命令。文件行号必须经过核实。

严重程度按用户影响判断：

- **P0**：关键任务无法完成或界面大面积不可用，必须优先修复。
- **P1**：严重阻碍使用、核心交互失败或重大的可访问性障碍。
- **P2**：存在绕行方式的体验问题、局部适配或一致性问题。
- **P3**：不影响主要操作的视觉与交互细节优化。

不要为凑满等级或数量制造发现，也不要将纯审美偏好提高为 P0/P1。报告末尾给出可直接使用的后续请求，例如“根据本报告修复所有已确认的 P0 和 P1，保留现有功能与品牌风格，验证后更新问题清单”；遵循 critique 的收尾要求，但不要让提问阻止完整报告的展示。

修复通常继续使用 Impeccable 的 harden、adapt、clarify、optimize、layout、typeset 或 polish 等流程，无须切换 Taste。只有用户要求整体视觉改版时，再考虑 Taste 或 Impeccable 的 redesign 流程。
