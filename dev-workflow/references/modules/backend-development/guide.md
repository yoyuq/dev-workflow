# 后端实现

为开发工作流提供明确的后端实现与验证规范，也可通过 `$backend-development` 单独调用。按项目选技术栈，不预设语言、框架或数据库。

## 确定项目事实

读取适用指令、依赖与锁文件、现有入口、相关业务模块、数据库迁移和测试。优先复用已知信息，记录实际框架版本、运行命令、验证命令和测试依赖。

已有项目沿用其结构。新项目缺少技术选型或重要业务规则时先澄清；由 `dev-workflow` 调用时复用其 `grill-me` 结果。无人值守时将未决关键规则记为阻塞，不自行选择新技术栈或改变产品语义。

## 先明确行为与接口

- 从调用方和验收条件确定输入、输出、错误、权限以及持久化行为。沿用现有 OpenAPI、schema 或类型定义；只更新受影响的契约。
- 现有接口优先保持兼容，确需改变时明确调用方及迁移方式。不要只改返回字段而遗漏前端或下游消费者。
- 将业务规则与传输、存储适当分离，遵循项目现有模块边界；不为小功能引入无需求支撑的微服务或通用框架。

## 实现要求

仅在相关能力确实涉及本次改动时应用以下规则：

- **数据与权限**：在服务端校验输入及资源访问权限，区分身份认证与资源授权；不依赖前端隐藏按钮或客户端传入的角色作为授权依据。
- **状态变更**：明确事务边界、约束和失败后的状态；涉及重复请求、消息重投或外部回调时按业务设计幂等及去重，不能仅重复重试整个写入。
- **数据库变更**：使用项目迁移机制，检查旧数据兼容、约束与回滚/修复路径。在隔离测试数据上验证；编写迁移不等于获准执行生产迁移。
- **外部依赖与后台任务**：使用明确的超时与有限重试；区分可重试失败和永久失败。测试隔离第三方写入和付费调用，不能将模拟依赖结果说成真实集成验证。
- **错误与日志**：沿用统一错误语义，保留必要诊断上下文，避免将密钥或敏感正文写入日志；不吞掉失败并返回成功。
- **查询和资源使用**：沿用分页与容量约定，关注改动引入的无界查询、N+1 和资源泄漏。性能结论须有测量依据。

框架和依赖 API 不确定时，查证与项目版本匹配的官方文档后再实现。

## 验证与收尾

根据 [验证矩阵](references/verification.md) 选择本次需要的检查，不照表执行无关项目。新增业务规则或可复现缺陷优先用行为测试覆盖，再完成实现；需要完整测试优先流程且已确定接口与范围时使用可用的 `tdd` 技能。

先运行相关基线检查，区分既有失败。实现后执行受影响的测试与项目要求的构建/静态检查，验证契约和关键失败路径。修正当前改动造成的问题，检查通过后避免无依据地扩大测试或重构。

交付说明行为变化、涉及的接口/数据变更、真实执行结果和未验证部分。全栈任务回交前端可直接使用的接口事实并完成联调。用户未要求或未授权的部署、生产数据操作不属于本技能默认范围。
