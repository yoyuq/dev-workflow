# 按场景执行

只阅读与当前任务对应的章节。新目标先遵循 [需求对齐](requirements-alignment.md)，记录真实确认后再按 [模块拆解与执行计划](planning.md) 推进；已有项目流程可与协作规则组合。

## 新项目与较大功能

输入：用户目标、目标目录、已有约束；现成规格、设计和代码优先复用。

1. 按 skill-routing.md 使用 grill-me 明确用户流程、首个可交付范围、关键数据和验收行为；复用已知答案。界面体验不确定性优先用可运行原型解决。
2. 沿用指定技术栈和现有环境。技术选型尚未确定时，比较与该项目有关的少量方案，查证会影响实施的当前文档，说明选择依据。
3. 先完成模块清单，再编写执行计划书，列出模块职责、接口、依赖、任务顺序与验收。保存位置和内容遵循 planning.md；复用已有规格。小项目可在同一记录中保存简短模块说明、计划和证据。
4. 前端默认读 frontend.md，后端按 backend-development 沿用项目技术栈；具体设计工具按 skill-routing.md 选用。先统一全栈接口，再打通一条真实功能路径并建立必要验证。后续按用户价值与依赖顺序扩展。
5. 涉及界面时运行可用的浏览器或预览检查关键交互、空状态和错误反馈。涉及接口或批处理时验证真实输入输出。工具不可用时说明哪些行为未验证。
6. 交付实际可用结果、复现/启动方式和验收证据。用户要求部署且已有必要权限时继续部署并检查部署结果；否则按本次约定终点收尾。

## 已有项目

输入：变更目标或缺陷现象、相关项目、现有工作状态。

1. 检查工作树与相关实现，定位行为入口、调用方和已有测试。运行与改动相关的基线检查，或复用同一代码状态下可靠的近期结果；无需每次小改动都运行全部测试。
2. 修复缺陷时先复现，记录预期、实际结果与环境条件。暂时不能复现时保留假设和不确定性，不凭猜测宣布根因。
3. 按需求对齐规则确认本次预期行为（同目标可引用已有确认），再拆到相关模块，编写或更新执行计划书，开始修复、扩展或重构。沿用现有架构及公共接口约定，按 skill-routing.md 使用指定前后端技能；重构时明确需要保持的可观察行为。控制改动范围，只有实现当前任务确实需要时才调整相邻模块。
4. 实现后验证目标行为及受影响的回归路径。区分基线已有失败、本次新增失败和环境阻塞，不为了通过检查而删掉有效断言或降低验收标准。
5. 对照最终差异检查遗漏。检查通过后停止无证据的重复测试，完成所需文档和交付。

## 协作

适用于多人共同修改的项目；只有用户或适用指令已经授权代理协作时，才使用多代理工具。

- 复用项目的分支、PR、评审和 CI 规则。并行修改采用独立分支或 worktree；先检查可复用工作区，避免覆盖他人改动。
- 每项可并行任务说明目标、负责文件或模块、接口约定、依赖、验收证据与负责人。共享数据结构、依赖锁文件等冲突面先协调，强耦合改动顺序实施。
- 分工以可独立验收的任务为单位。无需为简单任务同时创建产品、架构、开发、测试等多个角色。
- 独立审查者接收原始需求、最终差异、验证结果及必要项目约束。审查发现由实现者核对证据后修正；不能把所有建议都自动接受。
- 集成人负责最终集成状态的检查；各分支通过不代表合并后通过。PR 描述解释行为变化、相关验证和重要限制。
- 需要发消息给同事、创建外部任务或安排发布时使用用户实际授权，不从“团队项目”一词推导额外权限。
