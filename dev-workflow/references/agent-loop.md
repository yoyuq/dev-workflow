# 当前 agent 的推进循环

这份协议让活跃的 agent 在一个总目标下连续推进。包内 [串行控制器](runner.md) 已实现跨 CLI 调用、失败反馈、验收与恢复。机器关机后持续运行仍需把控制器部署到独立服务器，并配置该主机的进程守护和运行环境。

## 目标与滚动计划

新目标先完成 [grill-me 需求对齐](requirements-alignment.md)，记录用户确认的目标、完成条件、授权终点、约束和运行/重试限制，再拆功能模块并写计划。当前代码基线由实际检查获得；短任务不必建立庞大文档体系。续跑引用已有确认，不重复访谈。

保持目标与验收条件稳定，计划可以随着事实变化修订。每次修订记录版本、依据、受影响任务和新的验证步骤；保留旧记录以便解释为何改变方法。改变产品目标或授权边界属于用户决定。

## 每一轮

1. **读状态**：确认真实工作区、分支与计划对应；从错题本检索当前模块、技术栈版本、错误类型相关的少量记录。
2. **选任务**：只选择依赖满足的任务，写出这一步的预期可观察结果及检查方式。选择已经授权且能推进目标的最小有效步骤。
   用简短任务卡列出目标、输入、允许范围、验收、相关指南和上轮反馈；全局模块/计划已有时不重做。控制器从固定计划自动生成本轮卡片。
3. **执行**：读取必要的内置模块，实现或诊断。不为每个小步骤重复审批，也不无依据地扩展工作范围。
4. **观察**：实际运行相关检查，保存命令、退出状态、代码状态与证据。区分产品错误、环境限制、验证不足和未决决定。
5. **反思**：比较预期与实际。通过时说明哪些验收项得到证实；失败时提出有证据的新假设，或记录阻塞。反思以短决策记录为主，不保存冗长内部推理。
6. **落盘并继续**：更新进度、必要经验和下一步。仍有可执行任务就继续；依赖阻塞项的任务等待，独立任务可在工作区状态清晰时推进。每条路径完成后对照范围表找剩余承诺，必要时细化未开始节点并记录原因；不能把总目标改成“基础版”来提前交付。

若任务未约定尝试上限，同一错误连续两次没有新证据或进展时，停止重复同一动作，转为进一步定位或明确阻塞；这不等于整个目标结束。不要反复生成计划来代替实施。

## 结束与恢复

- 完成：当前最终代码满足所有相关验收条件；待人工验收不算全部完成。
- 阻塞：写明不可继续的原因、已尝试方法、证据和需要的最小决定/环境变化。能完成的独立工作仍继续。
- 预算或宿主停止：保存最近实际状态与下一步，未执行检查标为未执行。提示词中的预算不是硬限制。
- 恢复：重新检查代码/环境和进度记录是否一致；证据过期则重验受影响部分。从第一个未完成且依赖满足的任务继续。

夜间 v4 固定计划是另一种执行约束：模型不能自改固定计划、范围或验收。发现必须重规划时保留现场，结束当前轮并生成新的准备快照；未来控制器可接续新轮，但不能把旧轮强行标成完成。

当前控制器可自动调整同一任务内的实现方法、反馈失败、选择依赖满足的下一任务；新需求、新模块或修改验收仍进入准备阶段。没有无限扩张目标的“自我任务生成”。
