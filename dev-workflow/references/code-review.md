# 需求与代码检查

先读取原目标、验收条件、允许范围、基线与最终 diff、实际测试证据。分别回答：是否实现了要求的行为；实现是否存在具体缺陷或维护风险。

检查接口和边界、错误处理、数据一致性、权限与资源生命周期，以及测试是否能暴露所担心的问题。发现问题时给出可定位的位置、触发条件、影响和证据。先核实疑点，避免将个人风格偏好当成缺陷。

如当前任务允许且工具可用，可使用独立审查者并提供相同基线、规格和证据；否则在当前上下文自审并如实标注。不要把换角色提示词称为独立审查。

修复阻断验收的问题后重跑受影响检查。保留未处理事项及原因；不能通过删除验收项或降低断言让审查“通过”。完成报告映射回原需求，不只列新增文件。

## 独立控制器的审阅提速

审阅工作区从待审提交新建。控制器先在这里实际执行已固定的检查，记录命令、工作目录、退出码、耗时和日志哈希；失败立即阻断，不启动模型来覆盖失败。模型检查测试覆盖，读取需要的证据，对未覆盖风险和旧阻断反例独立验证。无需为证明「自己又跑过一遍」重复同一条已通过命令；报告必须区分控制器检查与模型亲自执行的补充探针。控制器可用的工具不等于模型沙箱也可用，不把不可用验证写成通过。

控制器将不超过 24 KiB 的 `brief.json` 直接送入审阅入口；简报与 diff 合计不超过 48 KiB 时也附上完整重点 diff，减少开场文件读取，避免命令输出截断。较大输入仍完整保存在文件中按需读取，不截掉内容。完整命令、历史验证与证据路径保留在 `context.json`。首次审阅使用任务完整 diff。修复复审只有在前次任务、契约版本、计划修订和启动基线一致时，才生成前次提交到当前提交的 `focus.patch`，并保留 `changes.patch`。所有相关阻断项仍需复现，新增代码及受影响调用方仍需检查；历史不足、范围扩大或发现新风险就展开完整审阅。空增量不能消除未解决问题。

小型修复若完整 `context.json` 不超过 24 KiB，则直接提供完整索引替代简报；索引与两份 diff 合计不超过 64 KiB 时，也一起提供任务完整 diff，避免先读摘要后再补读同一批材料。较大修复仍走增量索引和按需展开。

最终整合审阅始终检查整个分支及跨模块行为。简报、增量、完整 diff 和本次检查日志均在模型运行后核对哈希；源码和 HEAD 也必须保持不变。记录中的 `timing` 分别给出总耗时、固定检查耗时和模型耗时。没有降低模型配置、缩短超时、删除验收或用旧审批代替新提交审阅。
