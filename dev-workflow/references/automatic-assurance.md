# 自动检查与有限恢复

准备新运行时，AI 根据本次改动、模块依赖和匹配的错题记录选择补充风险检查，写入固定计划。涉及共同配置、数据库或启动时检查真实共享实例和适用顺序；新增测试必须实际运行，不能仅检查文件存在。检查使用项目技术栈，不要求全部项目使用 Python。

协作计划可声明 `assurance: {checks: [...]}`。每项沿用 verification 的 `id/argv/cwd/timeout_seconds`，另有 `task_id`（现有负责人的任务 ID）和 `risk`（为何原验收可能漏掉此路径）。脚本必须在开工前置于项目之外并固定摘要；不能在运行中由模型追加任意命令，也不能替换原需求或固定验收。

总控在该任务提交前、独立审阅基线、集成和最终验收中实际执行补充检查。任务提交前失败使用原来的失败证据、错题本与工作者返工通道，保留尝试次数和剩余时间，不需要宿主临时创建补测。原验收即使通过，也不能跳过失败的补充检查。检查内容、源码不变和 Git 范围继续受原约束保护。

这是预先声明的风险检查闭环，不保证自动发现所有未知缺陷。独立审阅仍负责检查覆盖和新风险；超出已授权范围或缺少业务决定时保留阻塞并向用户说明。

`assurance.max_final_repairs` 可选 0–2，默认 0。明确属于预设补充检查、不是超时的最终基线或审计失败，可在静止检查点交回其已声明负责人，继续使用原文件范围、尝试和总时间。其他已集成实现保留；负责人修复后必须重新做完整验收和整个分支审阅。未归属的失败、取消、人工决定或耗尽预算仍阻塞，不猜测负责人、不新增检查或修改业务目标。

`review.max_recovery_attempts` 可设为 0–2；未声明为 0，保持旧计划行为。每次恢复都另起独立审阅上下文，重新核对绑定、源码、固定输入并运行新基线。仅进程无进展、单次时限或退出失败允许有限重试；取消、明确权限拒绝、认证/额度/模型不可用、输入或源码漂移、无报告及错误绑定不会自动放行。失败过程与恢复事件记录到报告。恢复计数按 Git/契约/计划绑定持久保存，恢复会话不刷新次数；所有调用仍受 review.max_rounds 和原运行总时限限制。

2.13 的 read-tools 审阅进展识别继续适用。成功工具完成只能证明操作进展；失败进程留下的草稿报告不能取得批准。工作者仍使用 artifact 看护。不会修改旧技能快照、旧失败结果、模型配置或权限设置。
