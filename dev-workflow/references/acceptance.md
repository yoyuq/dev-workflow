# 验收覆盖与计划一致性

本规则连接用户需求、模块拆解、执行计划和交付证据。交互开发用简短表格表达即可；夜间执行使用 v4 结构，由检测脚本核对。保持原有“先模块拆解，再写计划，最后执行”的顺序。

项目改造交付前逐条对照原始诉求和 [范围表](plan-depth.md)：本轮实现必须有当前代码的结果证据；已有满足核对旧依据是否仍适用；延期与不涉及保留实际用户依据。未完项、待人工验收与未运行检查明确列出。改动行数、节点数量和计划 ready 都不表示项目已完成；打通第一条路径不能替代其余已确认范围。

## 分层验收

准备阶段分别考虑下列维度，为适用的条件添加 layer（旧条件默认 functional）。不适用的维度在计划中说明，不以统一长清单拖慢小修复。

| layer | 要回答的问题 | 有效证据示例 |
| --- | --- | --- |
| functional | 功能是否按真实操作工作 | 行为测试、API/数据库集成、浏览器操作 |
| specification | 是否满足用户要的边界和场景 | 需求到断言的对应、错误路径、人工需求审阅 |
| quality | 实现是否符合项目维护要求 | 有针对性的静态分析、兼容性/性能检查、代码审查 |
| visual | 界面是否可用且符合设计方向 | 实际视口截图、键盘/响应式检查与人工视觉判断 |

layer 只分类，不决定 automated/manual。质量与规格审查没有可执行断言时应明确人工待审；截图存在、编译通过、模型自述好看都不能自动通过 visual。自动浏览器可验证交互和布局边界，审美判断仍需相应证据与审阅。

控制器生成 layered-acceptance.json，引用最终独立验收日志与提交。未设条件的层为 not_assessed；缺证据为 unverified；待人工验收保持 incomplete/awaiting_review。不会因为功能测试通过就声明四层均通过。

## 验收覆盖

为本轮需求分配稳定 ID。每项任务的验收条件有任务内唯一 ID、可观察描述、对应需求 ID、自动或人工验收方式。每条本轮需求至少对应一条验收条件，每条自动条件至少对应一个真实检查 ID，检查 ID 必须存在于同任务的 verification 中。每个检查也应说明支持哪条自动验收条件。

```json
{
  "id": "AC-login-denied",
  "description": "错误密码不能获得有效会话",
  "requirement_ids": ["REQ-login"],
  "mode": "automated",
  "verification_ids": ["auth-integration"]
}
```

同一条件关联多个检查时，全部通过才能算自动通过。同一检查可覆盖多个条件，但必须实际验证对应行为；不能把 build、打印 OK 或无关测试绑定到所有条件来补齐表格。增加条件或改变检查需重新生成计划，不能只改报告。

需要人工判断的条件使用 `mode: manual`、空 `verification_ids` 和非空 `review_instructions`。例如确认页面是否符合用户选定的视觉方向；不能以截图文件存在代替审美判断。含人工条件的任务完成实现和自动检查后，在报告 pending_tasks 中使用 `awaiting_review`，不放入 completed_task_ids，整体不能是 completed。

检测器会验证这类任务的实际提交、范围和自动检查，返回退出码 3 并列出待人工验收项。它不会读取模型自写的“用户已批准”作为人工通过凭据。当前没有自动消费人工审批凭据的接口；用户的最终确认由外部交付记录保存。后续任务若依赖这项尚未验收的任务，也不能被报告为完成。

`audit.json` 的 acceptance 清单将需求 ID、条件 ID、检查结果、提交和日志摘要关联起来；未运行、失败与待人工验收分别记录。预检通过不会产生任何“自动条件已经通过”的证据。

这些规则能发现漏项、无效引用和证据缺失，不能理解自然语言需求或证明测试充分。准备阶段审查断言与需求是否相符；关键独立验收测试由控制器固定版本，避免实现过程同时弱化测试。

## 模块依赖对应到任务

模块的 depends_on 表示需要另一个模块的前置产物。承担消费方工作的任务，使用 module_dependencies 指定哪个任务提供必要产物，并在 depends_on 中建立直接或间接的前置关系。

例如模块 M-ui 依赖 M-api 的接口契约，由 T-contract 提供：

```json
{
  "id": "T-ui",
  "module_ids": ["M-ui"],
  "module_dependencies": {"M-api": ["T-contract"]},
  "depends_on": ["T-contract"]
}
```

上述片段只展示依赖字段，完整任务仍需目标、范围、技能和验收等内容。T-contract 必须属于 M-api。前置产物具体是什么，写在任务目标和模块输出中。无需等待提供方模块所有工作都完成；绑定真正需要的接口或产物即可。若同一个任务负责依赖两端模块，可以在该任务内协调，内部模块边不要求自己依赖自己。

检测器拒绝遗漏或多余的模块绑定、未知或不属于提供方模块的任务、缺少任务前置路径的绑定。模块 DAG、任务 DAG 和两者的绑定都必须有效。它不能证明任务描述中的产物确实满足调用方，仍需接口与集成检查。

## 计划书和任务清单使用同一份准备数据

先完成模块清单，再写目标、任务步骤和验收安排。交互开发可使用 Markdown 模板；夜间模式将这些内容填写到 v4 准备 JSON，通过 `render-plan` 生成正式计划书：前半部为可读的需求、模块、执行顺序和验收表，附录保存准确的命令及运行约束。

渲染命令只写新文档，不修改输入 JSON，也不授权开工。把返回的路径和摘要填入 execution_plan，内容就绪后设置 ready，再由外部控制器固定 JSON 摘要。控制器在编码前完成这一步。

开工和交付检查重新生成期望文档并对比实际内容，即使重新计算了文件摘要，也不能用不一致的文档代替。准备数据的 status 从 draft 变为 ready，以及计划书自身的 execution_plan 路径/摘要，不参与文档内容，避免循环引用。其他准备字段均进入文档。

不要在生成文档里单独修改任务范围或顺序。准备阶段先修改同一份数据，再生成新版本；运行中的新关键决定保留为阻塞，重新准备下一轮计划。计划书存在、内容一致也不证明业务方案正确，应在开工前审查一次需求完整性、接口兼容和测试有效性。
