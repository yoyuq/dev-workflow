# 人工答复与原任务续跑

适用：统一入口的 quick/full 及 coordinated v2 计划。旧串行 v4 保持原恢复流程。用户已确认范围内的补充答案和人工验收可写入原运行；实现任务调整见 [受控重规划](replanning.md)，改变目标、验收、预算或授权仍需要重新对齐和准备快照。

## 接收真实答复

宿主先把待答问题呈现给用户，收到实际回答后再提交。不要让工作者或 AI 协调者编造用户回答。总控无可执行任务时结束进程，等待时间不消耗执行预算；响应命令接收答复后唤起原运行，无需定时任务。

```text
python <WORKFLOW_ROOT>/scripts/workflow_coordinator.py human-requests --run-dir <run-dir>
python <WORKFLOW_ROOT>/scripts/workflow_coordinator.py respond --run-dir <run-dir> --response <response.json>
```

`human-requests.json` 同时在执行检查点导出。复制所选条目的 `ticket_id`，填写 [答复示例](../assets/human-response.example.json)：`id` 是本次答复的稳定唯一 ID；`text` 是具体答复或审阅结论；`reference` 与 `quote` 记录真实用户答复的出处和原话。原始答复文件放在控制器输入目录，不放工作者邮箱。

- `decision: answer`：回答该凭据对应的一个必要问题。所有必要问题解决后，原任务获得一次剩余预算内的尝试，必须读到并确认答复，再执行并接受独立验收。多个问题逐条回答，不因一个答案清空其他问题。
- `decision: approve`：确认条目列出的全部人工审阅项。审阅 `context.review_head` 对应的提交及该任务 `allowed_scope` 的内容；候选工作区只用于查看，不能手改。自动检查仍重新执行，通过才发布里程碑和释放依赖。
- `decision: reject`：记录具体修改理由，任务及依赖成果失效，使用原预算重做，保留原提交和现场。拒绝不回退已存在的集成历史；新尝试从当前集成提交修正。

签收范围是任务允许修改的文件/目录及共享约定。需要人工审阅跨模块整体行为时，把这些依赖路径纳入审阅任务的范围或共享约定；范围之外的普通文件变化不会自动作废此项审阅。范围内代码变化会在集成或最终验收时要求再次审阅，不沿用旧签收。

## 一致性与恢复

凭据绑定运行、固定计划摘要、任务、尝试、提交、集成基线及共享约定版本；审阅凭据还绑定实际候选的文件摘要。上下文变化后旧答复被拒绝，重新读取凭据并核实后提交。计划与验收文件的固定摘要漂移仍直接阻止执行。

答复先进入 SQLite 队列，控制器在自己的循环中应用。响应进程不会直接覆盖任务事实。状态、消息和应用回执在同一事务提交；崩溃前未提交的答复仍留在队列，恢复后只应用一次。同 ID 同内容重复提交返回原回执；同 ID 不同内容被拒绝。过期答复有 rejected 回执和原因，不改变任务。

控制器仍在运行时，`respond` 等待应用回执；已停止时该命令启动原运行。响应恰好遇到控制器退出时会接续未处理的队列。操作命令中断后答复仍保留，重新提交同一个文件或 `run` 可继续处理。宿主应查看最终 `status`/`delivery.json`，applied 只表示答案已接收，不代表项目完成。

停止请求不会被自动解除；中断需 `recover`，取消需显式 `clear-cancel`。运行时间、尝试次数、协调轮数不重置；预算耗尽时保留答案并报告剩余任务。模型不能通过 reply/retry 绕过已记录的必要人工决定。

这是合作式本地控制协议，不是用户身份认证服务。同一账户下的恶意进程仍可能改写文件；服务器部署需由可信宿主接收实际人类答复，并用账户/容器权限隔离控制目录。JSON 引用只能提供审计线索，不能证明答复真的出自用户。
