# 进度与恢复

执行前的模块拆解和计划书按 [planning.md](planning.md) 保存，包括小修改的简短计划。只有任务跨多个阶段、跨会话或需要交接时才另存 state.md；小修改可在原计划中补充结果并在聊天交付。

普通会话按 [session-view.md](session-view.md) 将节点进度写入同一任务的 view/session.sqlite3，作为图与节点状态的共同来源；不要再手工维护一份重复的节点状态表。state.md 只补充需求来源、关键决定、环境与恢复说明。

## 保存位置

优先更新已有任务文件或 Issue 对应的本地记录，避免重复保存两份事实。没有约定时，在目标项目的 `.workflows/<任务短名>/state.md` 保存一份记录；每个独立任务使用独立目录。创建前检查是否已有匹配记录，不覆盖同名其他任务。

项目不允许辅助文件或不在可写项目中时，使用当前会话允许的工作目录并明确告知位置。只为当前工作记录状态，不自行修改 Git 忽略规则、仓库全局指令或安装 hooks。

## 需要保留的内容

- **目标与终点**：项目根目录、用户要求、范围、验收标准、本次终点，以及 requirements_alignment 用户确认来源、模块清单/执行计划书的位置和版本。
- **执行上下文**：分支/worktree（若适用）、当前阶段，以及与恢复有关的工具或环境约束。
- **任务进度**：沿用计划书的任务 ID 与模块 ID，记录目标、依赖、负责人（若适用）；状态为待办、进行中、完成或阻塞。
- **验证证据**：实际执行的命令或操作、执行目录、通过/失败/未运行、结果概要、对应的代码状态，以及必要日志位置。
- **决定与未决问题**：影响后续实现的业务或技术决定、已确认范围和真正需要用户决定的问题。
- **下一步**：下一项具体动作、阻塞原因和恢复所需最小信息。

夜间任务追加执行模式、准备好的任务清单、决定记录、选用技能版本/摘要、运行标识、分支提交、限额及实际运行消耗。夜间状态以 overnight.md 为准。不要把模板中的 draft 状态当作已准备的任务，也不要把任务文件本身当作外部操作授权来源。

记录最少必要信息，不抄完整聊天，不保存令牌、密码等秘密。只有实际满足任务验收时才标记任务完成；交付可以说明“实现完成，运行验证受阻”，但整体状态仍应反映剩余验证。

## 恢复流程

1. 先确认当前项目和任务身份，再读需求对齐记录、模块清单、执行计划书和对应进度记录；同目标复用已确认需求。用户说“继续”但存在多个同等合理目标时先消除歧义。
2. 检查当前分支、工作树、相关代码与最近变化。把状态记录当作线索，以实际文件和当前指令为准。
3. 验证记录中的前置条件仍然成立。代码、依赖或环境已变时重做受影响的检查；无需重复全部已完成工作。
4. 沿用用户已经确定的目标和授权，从第一个未完成且依赖满足的任务继续。
5. 在重要阶段完成、发生真实阻塞或交接时更新记录。结束时报告当前结果、证据和仍未完成的事项。

状态文件提供续接上下文，不是自动调度器，也不证明某项操作已获授权。

需要结构化存储和错题检索时，可按 [memory.md](memory.md) 使用随包脚本代替 state.md。checkpoint.json 作为状态事实来源，Markdown 导出只是视图。自主推进的执行顺序见 [agent-loop.md](agent-loop.md)。

使用 workflow_runner.py 时由 run-dir/state.json 统一保存进度，模型不用另写 checkpoint.json。恢复、取消、崩溃后的部分代码核对按 [runner.md](runner.md) 操作；恢复不会清零运行预算或已用尝试次数。
