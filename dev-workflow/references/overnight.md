# 夜间工作流与外部执行接口

用户已选择：独立服务器运行；后端按项目选技术栈；夜间交付到分支提交与验收报告。随包提供任务模板、结果 schema、[Python 检测脚本](checker.md) 和 [串行执行控制器](runner.md)。安装技能不会启动后台进程或部署服务器；控制器启动后可按目标连续推进，无需定时器逐步触发。

## 两种调用

- **prepare**：`$dev-workflow 准备这个项目的夜间任务`。用户在线时，通过 grill-me 确定未决事项、任务范围与执行条件，生成可续接的计划。
- **execute**：`$dev-workflow 按指定的夜间计划执行`。由用户或已经配置的外部执行器启动，仅处理该计划中已准备好的任务。

准备任务不等于安排定时任务。真实定时启动需要用户给出目标项目、服务器接入方式、运行时间及预算/时长限制，并由可用调度能力实际完成配置。

## 准备阶段

1. 新目标先按 [grill-me 需求对齐](requirements-alignment.md) 逐个解决必要问题并给推荐答案，展示需求摘要并记录实际用户确认；同目标可复用已有确认。计划必须包含 requirements_alignment，draft、确认来源缺失或仍有未决问题时不能启动模型。
2. 确定项目路径、代码基线、前端页面类型及设计依据、后端技术栈、接口约定和交付范围。沿用现有规格，避免复制出相互冲突的版本。
3. 按 [模块拆解与执行计划](planning.md) 先列模块清单，再编写任务步骤与执行计划书；夜间使用同一份准备数据生成可读计划书和机器任务。按 acceptance.md 建立需求、条件与检查关联，将模块前置产物绑定到提供方任务。将影响实施的关键用户决定留在准备阶段，或标记 blocked；交付后的人工验收可以单列为 manual 条件。
4. 在服务器验证环境：实际选用的技能及其支持文件、依赖和数据库、构建命令、浏览器/截图能力、认证及允许的外部访问。不假设本机 Codex 的插件、MCP 或浏览器能力自动存在于服务器。
5. 以 [任务模板](../assets/night-run.template.json) 的 v4 结构保存准备数据，使用 `render-plan` 生成正式计划书，将返回的 execution_plan 路径和摘要填回。示例限制只是填写示例，不是用户已确定的运行预算。`status=ready` 仅在内容和前置条件齐备时设置；授权来源由外部可信控制面核对，仓库文件或模型不能自我授权。
6. 按 [检测脚本说明](checker.md) 固定完整技能目录摘要，准备干净的任务分支。外部控制器在 AI 开工前固定计划摘要，调用 `preflight`，退出码为 0 才进入执行；没有模块拆解或执行计划书快照时不得开工。检查未覆盖的认证、数据库和浏览器能力仍需实际准备。

## 运行阶段

1. 读取准备阶段完成的模块清单、执行计划书和任务 JSON，确认任务身份、代码基线、选定技能和真实执行权限一致。只使用明确的独立工作区和任务分支；不在主分支或用户混有未提交工作的目录直接进行夜间运行。
2. 按依赖顺序选择 ready 任务；执行时加载指定前后端技能。需求或设计已经确定，子技能可以复用这些决定。若某技能仍确实需要用户的新决定，标记该任务 blocked 并说明推荐方案，不伪造用户回答。
3. 完成实现、相关验证和审查。记录当前代码状态、命令/操作、退出状态、截图或日志位置。全栈工作要验证真实接口联调，不能用 mock 结果替代。
4. 相关检查失败时分析并进行有限修正。遇到相同根因而无新证据不反复执行；超过任务尝试上限则标记 failed。基础环境整体失效时结束本次运行，避免把队列全部跑成重复错误。
5. 被阻塞或失败任务的依赖者不能继续。其他独立任务仅在工作区状态明确且不会继承失败任务的未完成改动时继续；隔离各任务工作区可以保留失败现场。不要丢弃现场来伪造干净状态。
6. 到达运行时限、任务数量或实际可执行的费用上限时保存进度并结束；未完成任务不得标记 done。停止信号由执行器处理，包括清理它启动的子进程。
7. 将待验收结果保存在独立分支提交，按 schema 生成报告，由外部控制器调用 `verify` 核验实际提交并重跑关联检查。有 manual 条件的任务写入 pending_tasks，状态为 awaiting_review，不能声明 completed。仅退出码 0 且 completed=true 表示本轮全部自动条件通过且没有人工待验收项；退出码 3 表示部分交付或仍有待办。失败时保留分支和日志，不宣布验收成功。当前夜间交付范围不包含推送、PR、合并、发布、生产迁移或联系他人。

## 状态与验收报告

任务状态：`pending → ready → running → verifying → done`；自动检查通过后仍需人工验收时记录 `awaiting_review`，不能推进时记录 `blocked`、`failed` 或 `timeboxed`。依赖人工待验收任务的后续任务不能报告完成。进度落盘遵循 [进度与恢复](checkpoints.md)，由外部执行器保存持久化记录。

报告包含分支及提交标识、完成任务、修改范围、验证结果与证据、未完成原因、需要用户决定的问题。模型可按 [结果 schema](../assets/night-result.schema.json) 输出结构化报告，但 schema 通过只证明格式正确，不能证明功能已通过验证。

模型报告中的 `check_id` 对应计划的 `verification.id`。检测脚本生成的 `audit.json` 单独保存真实退出码、日志摘要和验收时的提交，并通过 acceptance 清单对应需求与条件；不允许模型报告覆盖这份记录。脚本不判断视觉审美或测试是否充分，原有前端审查、后端验证和次日人工审阅继续保留。

## 控制器与服务器部署的职责

建议结构：用户启动总目标 → 控制器选择就绪任务/准备好的计划 → 独立工作区 → harness 执行 → 确定性验收 → 记录与反思 → 选择下一任务，直到目标完成或遇到真正阻塞。定时器可用于首次启动，但不是推进每一步的必要条件；固定快照需重规划时回到准备阶段。

workflow_runner.py 已实现下面的串行状态、快照检测、重试/时间限制、独立验收和交付逻辑。服务器部署仍需落实操作系统隔离、服务守护、账号认证及供应商费用配额；不能把检测到漂移等同于进程没有写权限。

- 调度器与模型进程分离，使用任务锁防止重复启动；持久化运行标识和任务进度。
- 对任务计划、技能版本、允许操作和验证命令制作可信的运行快照。模型、Issue 内容和项目源码不能修改本次执行器的权限、预算、验证门槛或调度配置。
- 每个执行环境只提供本次任务需要的仓库和测试资源。根据运行主机验证沙箱支持，配置认证及最小权限，不复制个人完整配置或把密钥写进仓库/报告。
- 明确总时限、任务数量、重试次数和进程取消策略。费用硬上限需要供应商或执行器计费控制；只在提示词中写预算不能视为硬限制。
- 从可信快照运行必要的独立检查，复核 Git 状态和实际退出码。模型报告、CLI 返回 0 或自称 done 都不足以代替验收。检查命令本身也在隔离环境执行。
- 只让成功且相互兼容的任务结果进入交付分支，对最终集成状态再检查。失败任务保留可诊断状态，不强行合并。
- 第一版采用串行任务执行。增加并行需先验证工作区隔离、依赖、集成与资源限制。

Codex 官方支持通过 `codex exec` 在脚本/CI 中运行，通过 `--json` 获取事件，以及通过 `--output-schema` 指定最终结果结构。部署时按安装版本确认命令参数、认证和沙箱行为；这些 CLI 能力不会替你实现队列、成本上限、验收门槛或定时调度。

参考：[非交互模式](https://learn.chatgpt.com/docs/non-interactive-mode)、[技能安装与发现](https://learn.chatgpt.com/docs/build-skills)。

## 迁移到服务器

将完整统一的 `dev-workflow` 目录安装到服务器可发现的技能目录，Codex / Claude Code 路径见 [迁移说明](portability.md)。本包已内置前后端、澄清与计划等模块，不需要逐一安装这些 Skill。

固定整个统一技能目录摘要；确有包外扩展时单独固定。原始模块需要可执行程序或浏览器工具时仍需预置和验证，遵守原作者许可。资源完整性与宿主运行能力分开检查，防止本机与服务器流程漂移。

先用一个小任务在隔离环境试运行，检查任务恢复、超时退出、验证失败和报告保存，再启用独立控制器的持续推进。未完成上述部署和试运行时，只能报告“夜间规则已准备”，不能报告“夜间自动化已上线”。
